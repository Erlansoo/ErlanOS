# M4 — AI Kernel API v0

M4 conecta el runtime del modelo con acciones reales del sistema por una ABI
versionada sobre IPC. La inferencia sigue fuera del kernel. Prototipo validado el
14 de septiembre de 2026; resultados reproducibles en [VALIDACION-M4.md](VALIDACION-M4.md).

## Recorrido

`teclado → Mind (L3) → petición tipada → system (L2) → syscall con capability → kernel`

`mind/controller.e` se enlaza con el proceso `model` en este prototipo. El servicio
`system` es un proceso Ring 3 separado. El kernel crea un par de endpoints privados:
sólo `model` puede enviar peticiones y recibir respuestas; sólo `system` puede
recibirlas y contestarlas. El modelo no recibe la capability para cambiar el estado
directamente ni el derecho de presentación del compositor.

## Operaciones

| Entrada | Operación | Resultado comprobable |
|---|---|---|
| `/estado` | `ai_query` / op 1 | Instantánea con tiempo, memoria, hilos, cambios de contexto y modo |
| `/modo foco` | `ai_execute(1)` / op 2 | Paleta cálida de consola, panel y revisión incrementada |
| `/modo normal` | `ai_execute(0)` / op 3 | Restaura la paleta normal; repetir el modo no incrementa revisión |
| `/panel` | `ai_present` / op 4 | Panel de valores reales, separado de la zona de chat |
| `/ai <petición>` | Elección del modelo entre 0..4 | La acción elegida pasa por la misma ABI y recibe un recibo |
| `/ayuda` | Ayuda local | Lista de entradas |
| `/prueba` | Prueba de protocolo/permisos | Rechazos verificables sin cambiar modo ni revisión |

Las entradas directas son atajos deterministas: no se presentan como decisiones
del LLM. `/ai` sí ejecuta el transformer y compara los logits de etiquetas de acción
permitidas. El texto del chat ordinario nunca se interpreta como una orden.
El modo foco es **visual**; no cambia la prioridad del scheduler ni acelera inferencia.

El planificador acepta hasta 160 bytes y 192 tokens de contexto. Para cambiar modo,
exige una diferencia mínima de 2.5 logits respecto a la segunda etiqueta; es una
heurística de abstención, no una probabilidad. Las cuatro consultas inglesas del
README están verificadas en host. En español se probaron estado, foco y panel;
`Vuelve al modo normal` se abstiene, por lo que conviene usar `/modo normal`.

Las peticiones `/ai` consecutivas reutilizan sólo el prefijo de tokens idéntico de
la caché KV. La prueba real compara los cinco logits de una ejecución fría y otra
con caché y exige igualdad. Se recalcula al menos el último token; el chat o una
nueva carga invalidan la caché. En la prueba host: 78 pasos en frío, 6–7 para otras
acciones con el mismo prefijo y 1 al repetir exactamente la petición.

El System Graph v0 es una instantánea fija con nodos `system`, `memory`, `scheduler`
y `console`, relacionados por pertenencia a `system`. Su representación es el
registro tipado siguiente; todavía no hay enumeración general de objetos/aristas.
El límite físico de memoria incluye huecos; no equivale a RAM instalada/utilizable.

## Formato de intercambio

Enteros `u64` little-endian, sin punteros. El endpoint admite hasta 256 bytes.
Petición de exactamente 40 bytes:

| Offset | Campo |
|---|---|
| 0 | Versión = 1 |
| 8 | ID de petición > 0, creciente respecto a la última aceptada |
| 16 | Operación 1..4 |
| 24 | Argumento reservado = 0 |
| 32 | Flags reservados = 0 |

Respuesta de exactamente 104 bytes:

| Offset | Campo |
|---|---|
| 0, 8, 16 | Versión, ID, operación |
| 24 | Estado |
| 32 | Número de recibo del broker, creciente por arranque |
| 40 | Tiempo activo en ms |
| 48, 56 | Páginas físicas libres y límite físico en páginas de 4096 bytes |
| 64, 72 | Hilos vivos (incluye idle), cambios de contexto |
| 80 | Llamadas rechazadas por falta de capability |
| 88, 96 | Modo visual (0 normal, 1 foco), revisión |

Estados: 0 éxito; 1 longitud inválida; 2 versión; 3 ID nulo/repetido/antiguo;
4 operación desconocida; 5 argumento/flags; 6 error de syscall.
El broker valida todo antes de ejecutar y emite también recibos de rechazo por
serial. El cliente comprueba tamaño, versión, correlación, estado y recibo creciente.
Los recibos son evidencia de ejecución del prototipo, no firmas ni auditoría persistente.

## Permisos y compositor

`system` tiene CAP_SYSTEM (tipo 8, objeto 0) con derechos READ=1 y WRITE=2 en slot 7.
Las nuevas syscalls son mecánicas: 14 inspección, 15 modo, 16 presentación.
La syscall 17 consulta Escape con CAP_INPUT (`b=0`) o reconoce la cancelación
(`b=1`), siempre con `c=0`. El evento permanece activo entre capas del transformer
y no consume la cola de texto. Cancelar `/ai` invalida su caché y no envía una acción.
El derecho RIGHT_PRESENT=1 de CAP_CONSOLE permite el panel y los halos de acción
(estado 3) y autorización (estado 4).
`model` sólo conserva salida de texto y estados de espera/inferencia del halo.
`init` recibe inspección de sólo lectura para comprobar que escribir queda denegado.

Los buffers de log, consola e IPC se validan recorriendo las tablas de páginas del
proceso: presencia, acceso de usuario y escritura cuando corresponda. Se rechazan
rangos desbordados, destinos de sólo lectura y páginas no mapeadas. La asignación
anónima comprueba cuotas sin sumas desbordables y presupuesto físico antes de mapear.

El compositor v0 reserva una zona derecha; el chat no puede dibujar sobre ella.
La presentación sólo acepta un tipo de panel. No recibe texto arbitrario del modelo,
coordenadas ni acceso al framebuffer. `/panel` refresca la instantánea; el reloj del
panel no se actualiza continuamente. Cambiar modo también refresca el panel.
UI-01 añade el refresco por llamadas aceptadas a SYS_HALO cuando el panel ya se
ha mostrado, según la regla G5 descrita a continuación.
La salida de texto decodifica UTF-8 entre llamadas y usa glifos Latin-1 para
español; otros caracteres se representan con `?`.

## UI-01 — Trusted UI v1

La cabecera reserva los primeros 72 píxeles de alto. Su geometría depende del
ancho real del framebuffer: centro `cx=width/2`, `cy=36`, puntos de radio 5
separados 30 píxeles. El fondo continúa el degradado café del lienzo. Las etiquetas
son literales de `halo_name` en el kernel y se dibujan con la fuente 8×16 en
`(cx+70,28)` para los estados activos; IDLE sólo muestra los tres puntos.
No se aceptan cadenas, punteros ni coordenadas desde SYS_HALO o SYS_PRESENT.

| Estado | Etiqueta | Geometría adicional a los tres puntos | Color de puntos/etiqueta | Derecho sobre CAP_CONSOLE |
|---|---|---|---|---|
| 0 | IDLE (sólo en el panel) | Ninguna; cabecera sin texto | `fg` de la paleta | Sin bits adicionales |
| 1 | ESCUCHANDO | Anillo central: radio 10 `dim`, hueco radio 8 | `fg` | Sin bits adicionales |
| 2 | RAZONANDO LOCAL | Disco `dim` de radio 14 detrás del punto central | Azul `8a,b4,f8` | Sin bits adicionales |
| 3 | ACTUANDO | Contorno exterior de cabecera, 2 px | Ámbar `f8,c0,6a` | RIGHT_PRESENT=1 |
| 4 | AUTORIZACION | Contorno exterior y otro interior de 2 px desde `(5,5)` | Ámbar `f8,c0,6a` | RIGHT_PRESENT=1 |
| 5 | NUBE | Rectángulo de 2 px en `[cx-45,cx+45) × [21,51)`, violeta `c0,8a,f8` | `fg` | RIGHT_EGRESS=2 |

`fg/dim` son `d8,d8,de / 55,55,60` en modo normal y
`e8,d5,b5 / 65,59,49` en foco. Todos los dibujos permanecen en la cabecera.
La nube usa un rectángulo: un anillo de radio 52 no cabría en sus 72 píxeles.
`RIGHT_EGRESS` nunca se concede a ningún proceso. El broker conserva
RIGHT_PRESENT, y `model` conserva CAP_CONSOLE sin esos derechos. Mostrar el
estado AUTORIZACION todavía no implementa una confirmación humana; NUBE tampoco
implementa egreso de datos.

SYS_HALO valida primero la capability, luego el rango 0..5 y finalmente el derecho
requerido. Un estado fuera del rango produce ERR_ARG; los estados 3/4/5 sin su
derecho producen ERR_CAP y sus denegaciones específicas. `mind_selftest` comprueba
los tres rechazos desde el proceso model. Una llamada aceptada imprime exactamente
una línea de kernel `[halo] estado=N`, incluso si repite el estado. La traza vive
en `syscall.e`, después de `console_set_halo`; la función de dibujo no emite trazas.
`console_init` publica las dimensiones reales de rejilla y la línea
`[console] geometria header=... margen=... panel_x=... ancho=... alto=...`.

La entrada empieza en IDLE. Añadir el primer byte, incluido Shift+Enter, cambia a
ESCUCHANDO; las siguientes teclas no repiten la llamada. Borrar el último byte o
cancelar una entrada no vacía vuelve a IDLE. Enter vacío no cambia el halo. Una
entrada enviada pasa por RAZONANDO LOCAL y vuelve a IDLE tras el comando. El
broker añade ACTUANDO→IDLE sólo para operaciones aceptadas 2..4. Por eso los
comandos de consulta y `/prueba` tienen `[1,2,0]`, y modo/panel tienen
`[1,2,3,0,0]`. `/ai` añade su segunda llamada a 2 antes del plan.

### Recibo de presentación y filas verificadas

SYS_PRESENT mantiene `b=1`. El campo `c=0` sigue siendo un refresco compatible:
no cambia última operación ni recibo. Para `c!=0`, el broker empaqueta
`c=recibo*16+op`; el kernel obtiene `op=c&15` y `recibo=c>>4`. Sólo acepta op 1..4,
recibo positivo y estrictamente mayor al último presentado. Una entrada inválida,
repetida o antigua devuelve ERR_ARG sin mutar ni pintar. El entero empaquetado
permite como máximo un recibo de 60 bits; no se añade un protocolo de reinicio de
contador en este hito.

`system_present_receipt` guarda ambos campos, emite `[present] op=O recibo=R`
mediante `kprintf` y llama a `system_present`. Esa traza sólo existe en la ruta
validada de recibo iniciada por SYS_PRESENT; no se emite en refrescos ordinarios,
cambios de modo ni cambios del halo. El broker presenta op 2/3 después de cambiar
modo correctamente y op 4 para `/panel`, incluyendo su recibo creciente. Un error
de presentación produce estado 6 en la respuesta. El wire 40/104 bytes, los
opcodes y `audit()` no cambian.

El recibo y la operación son afirmados por el broker trusted y validados por el
kernel en rango y monotonía; no son una firma ni una reconstrucción independiente
de la acción. Los rechazos y consultas del broker también consumen números de
recibo, por lo que el panel puede saltar números entre presentaciones.

Se conserva la rejilla `x=panel_x+20+8*col`, `y=72+24+20*fila` y el máximo de
36 caracteres por fila. A los valores anteriores se añaden:

| Fila | Contenido fijo del kernel |
|---|---|
| 25 | `Actualiza con /panel`, conservada |
| 27 | `Halo: ` más nombre del estado actual; etiqueta y valor con colores distintos |
| 28 | `Ultima accion: ` más `consulta`, `modo foco`, `modo normal`, `panel` o `ninguna` |
| 29 | Número del último recibo; vacía antes de una operación presentada |
| 31 | `Destino de datos: local, sin egreso`, o `Destino de datos: NUBE (egreso)` en estado 5 |

G5: `panel_shown` se activa al presentar. Desde ese momento, toda llamada aceptada
a SYS_HALO invoca `system_halo_changed` y refresca la instantánea. Antes del primer
present, la región sigue vacía. El refresco conserva última operación y recibo.
`console_write`, scroll y las llamadas directas a `console_set_halo` no repintan el
panel; tampoco hay temporizadores, animaciones ni hilos nuevos. El límite conocido
es que el proceso model puede decidir **cuándo**, mediante sus estados permitidos
0..2, se refresca un panel ya visible. El contenido, las etiquetas y la geometría
siguen siendo del kernel; esto no certifica que el modelo esté realmente razonando.

### Pruebas de UI-01

`tests/m4/kernel_host.c` añade seis cabeceras distintas dos a dos, aislamiento de
texto y panel, refresco de la fila del halo sólo desde la syscall y validación de
derechos y recibos. Se conserva la comprobación original de cinco denegaciones:
el aserto del estado 4, ahora ERR_CAP, se ejecuta inmediatamente después para no
alterar el significado del contador anterior.

`scripts/qemu_m4_test.py` añade comprobaciones de secuencias de halo, correlación
de recibos de presentación, estado inicial y denegaciones de model.
`scripts/qemu_ui_test.py` usa su propia QemuSession y el modelo indicado por
`--model`; comprueba hashes de kernel y cuatro servicios contra lo preparado
para el arranque, y dimensiones leídas del serial. Decodifica píxeles con
`font8x16.h` exactamente, sin OCR tolerante, para contrastar modo, halo, acción,
recibo, revisión y denegaciones. Falla si falta Pillow o si una fila requerida
no cabe. Sus hitos PNG son `00-loading`, `00-idle`, `00-empty-keys`, `01-wrap`,
`02-foco` y `03-final`;
`result.json` conserva `ui_checks`, `frames` y evidencia por comprobación.

Estas pruebas arrancan VMs propias bajo `build/ui-test/` y `build/m4-test/`.
No acceden a la VM interactiva. No se inicia inferencia desde los comandos de UI,
aunque el servicio ejecuta su warmup normal antes de estar listo.

Corrección al encargo UI-01: la línea base de `init` contiene dos sondas denegadas,
Log con slot 5 y System.Write con slot 7, no sólo la segunda. La prueba visual
exige esas dos líneas exactas y que el panel cuente **todas** las denegaciones del
serial hasta el recibo de `/panel`; el valor observado antes de `/prueba` es 2.
No se elimina la sonda de Log ni se resta del contador para obtener el 1 que
preveía el documento del encargo.

### Lienzo café al iniciar — 2026-09-14

Por petición posterior a UI-01, el arranque normal muestra únicamente un fondo
café con los tres puntos arriba. Sustituye el fondo plano, la etiqueta IDLE de la
cabecera y el banner inicial previstos en el encargo original. La carga y el
warmup del modelo se registran por serial; los errores se siguen mostrando.
La primera tecla de entrada hace aparecer `> ` y conserva esa misma tecla.
Escape y Backspace, antes de escribir, dejan el lienzo intacto. `/ayuda` conserva
las instrucciones y los comandos disponibles.

El compositor dibuja un resplandor elíptico entre RGB `16,14,16` en los bordes
oscuros y `7a,60,4c` en el centro. Usa coordenadas normalizadas, aritmética entera
y dithering Bayer 4×4 de menos de un nivel por canal. No necesita textura,
asignaciones, FPU ni animación. Glifos, borrado, scroll y cambios del halo restauran
el color del fondo correspondiente a cada píxel. El panel conserva su superficie
separada y sus permisos de presentación.

La prueba visual comprueba el mismo lienzo durante la carga y tras readiness,
ausencia de texto y bordes de panel, sólo tres puntos en reposo, y aparición de
la primera entrada sin perder bytes. Las pruebas host comprueban además el
borrado sobre el degradado, UTF-8, entrada multilínea y límites de las superficies.
`test_input_host.py` incluye los stubs de warmup/contexto que necesitaba el bucle
actual para poder verificar el arranque silencioso y la entrada diferida.

## Verificación reproducible

En Git Bash con `source scripts/env.sh` y GNU Make 4.3 o posterior (4.4.1 en esta
máquina). La generación agrupada evita carreras entre C y headers al usar `-j`:

```bash
make all
make test
make test-m4-host
bash scripts/test_planner_host.sh --self-test
python scripts/qemu_m4_test.py
python scripts/qemu_m4_test.py --ai --timeout 1200 --command-timeout 600
make run
```

Las pruebas QEMU usan una copia privada de los binarios y GGUF, QMP por pipes,
logs propios y captura final en `build/m4-test/<ejecución>/`. Un timeout, excepción,
recibo incorrecto o fallo de prueba devuelve código distinto de cero. Sólo cierran
la VM que iniciaron. El modo `--ai` añade inferencia real, lenta con TCG.

## Límites de este hito

- SmolLM2-135M es una prueba de integración: elegir entre acciones acotadas no
  garantiza comprender cualquier petición ni resistir prompt injection. Los errores
  de interpretación siguen limitados a las operaciones concedidas.
- El planificador reutiliza la caché KV y reinicia el contexto de chat después de
  `/ai`. Aún no hay memoria persistente ni separación de contextos por agente.
- Un cliente y un broker, con endpoints fijos y llamadas síncronas. Recuperación
  de un broker caído, timeouts IPC y múltiples clientes quedan pendientes.
- No hay ventanas generales, voz, red, proveedor nube, ejecución de shell, compilador
  dentro del guest ni bucle de automejora. M6 necesita construir y probar esas piezas.
- Las pruebas actuales verifican los casos de permisos descritos; no constituyen
  una auditoría completa del kernel ni una garantía general de seguridad de Erlan.
